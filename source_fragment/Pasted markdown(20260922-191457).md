# DMX Native (`DimensionX/native`)

A self-contained Swift package: a **SwiftUI desktop GUI** for an installed `dmx` CLI, and a small **local observations helper** (`dmx-boundary-probe`).

This package is **independent of the Python backend**. It contains no backend code, links no backend code, and does not require the backend to build. It only speaks the CLI's JSON contract over a child process.

> ## Verification status — read first
>
> - **Compilation is UNVERIFIED here.** This source was authored on a Linux host with **no Swift toolchain available**. `swift build` and `swift test` have **not** been run, and the SwiftUI window has **not** been launched. Treat the code as reviewed-by-hand, not build-verified.
> - **macOS integration is UNVERIFIED here.** Nothing in this package was run on macOS, codesigned, sandboxed, or packaged.
> - **No runtime isolation is implemented.** This package creates no boundary, no container, no sandbox profile, and no per-app isolation. It does not claim to.
> - **No Windows execution is implemented.** There is no Wine spawn code, no loader, no emulation, and no execution path of any kind. `plan` results are displayed with `ready: false` semantics; the GUI never executes a target.
> - **An App Sandbox shared container is not per-app isolation.** The sandbox entitlement declared here is `false`, and no application-group container is declared. Nothing in this package should be read as an isolation boundary.
> - The only thing this package *does* to the outside world is run the executable **you** select, with the arguments it builds, and show you the JSON it returns.

## GUI usage (`DMX`)

1. Click **Choose dmx executable…** (`NSOpenPanel`) and pick your installed `dmx` executable. The GUI does **not** look for it, scan for it, or bundle it.
2. Optionally choose a **root path**, which the adapter inserts as `--root <path>` **before** the command.
3. Until a valid executable is selected, the app shows a clear disabled state and every command button is disabled.

Available actions:

| **ActionAdapter call**  |                                     |
| ----------------------- | ----------------------------------- |
| Refresh (profiles)      | `profiles list`                     |
| Choose EXE… + Create    | `profiles create NAME ABSOLUTE_EXE` |
| Choose file to analyze… | `analyze ABSOLUTE_FILE`             |
| Run plan                | `plan APP_UUID`                     |
| Run diagnostics         | `diagnostics APP_UUID`              |

Design notes:

- **No shell.** The adapter passes an exact `argv` array to `Process`. There is no `sh -c`, no string interpolation, and no glob expansion. A test asserts that an argument containing `; touch … #` arrives verbatim as a single `argv` element and that no shell action occurs.
- **Asynchronous and bounded.** Every command runs off the main run loop; results and errors are published back to the UI. Each captured stream (stdout and stderr) is capped at 4 MiB; exceeding it fails the call and terminates the child. A timeout terminates the child, `SIGTERM` is escalated to `SIGKILL` after a short grace period, and pipes are drained non-blockingly (never with `readToEnd()`) so a descendant that inherits a pipe cannot stall the call.
- **Not-executable state is explicit.** If the selection is missing, a directory, or not executable, the app says so and disables commands.
- **Accessibility.** Controls carry explicit `.accessibilityLabel`s; result rows are combined accessibility elements with descriptive labels.
- **Localization.** English and Spanish are switchable at runtime via a segmented picker. Strings live in `Sources/DMXCore/Resources/{en,es}.lproj/`.
- **No decorative UI.** There is no performance panel, controller, or launcher. The GUI shows CLI facts and nothing more.

## CLI JSON contract

The GUI and the tests consume exactly this contract. The native layer **reads** it and never emits it.

- Success: `{"ok": true, "result": <payload>}` with exit status `0`.
- Failure: `{"ok": false, "error": {"code": "...", "message": "..."}}` with a non-zero exit status.
- On failure the adapter throws `DMXCLIError.remote(code:message:)`.
- If stdout is not a decodable envelope the adapter throws `DMXCLIError.invalidOutput(status:stderr:)`.
- If `ok` is true but no `result` is present it throws `DMXCLIError.missingResult`; if `ok` is true with a non-zero exit it throws `DMXCLIError.statusMismatch(status:)`.
- If either captured stream exceeds the 4 MiB per-stream cap it throws `DMXCLIError.outputLimitExceeded(stream:limit:)` (code `output_limit_exceeded`) and the child is terminated.

### Commands and result shapes

| **Command`result` shape**           |                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| `profiles list`                     | array of `{id, name, artifact_sha256, runtime_digest (nullable), graphics, created_at}`           |
| `analyze ABSOLUTE_FILE`             | `{architecture, format, imports: [string], evidence: [{kind, value, certainty, source}], sha256}` |
| `profiles create NAME ABSOLUTE_EXE` | a single profile object (same shape as `profiles list` entries)                                   |
| `plan APP_UUID`                     | `{app_id, ready: false, blockers: [string], actions: [object]}`                                   |
| `diagnostics APP_UUID`              | a dictionary of safe local diagnostics (keys owned by the backend)                                |

Notes on modeling choices:

- `runtime_digest` is `String?` and is displayed as “None” when null.
- `actions` is modeled as `[JSONValue]` because the action object shape is owned by the backend. The native layer displays it as pretty-printed JSON and does not invent fields.
- `diagnostics` is `[String: JSONValue]` for the same reason.
- `plan.ready` is rendered as reported. This package treats `ready` as informational only and never acts on it.

## Probe usage (`dmx-boundary-probe`)

A local, deliberately narrow observations helper.

svg

```
dmx-boundary-probe --help
dmx-boundary-probe --json                    # entitlement observation only
dmx-boundary-probe --all                     # entitlement + loopback
dmx-boundary-probe --file /path/to/fixture   # scoped read attempt (repeatable)
dmx-boundary-probe --file a --file b --json
```

What it does:

- **Entitlement observation via `SecTask`.** Reads `com.apple.security.app-sandbox` and `com.apple.security.application-groups` from *this process's* task.
- **File observations, scoped to caller paths.** It only ever attempts paths you pass on the command line. It never enumerates, scans, or targets system paths. Only a *regular file* is opened (a non-regular target is rejected before `open()` is reached) and the open is non-blocking, so a caller-supplied FIFO cannot make the probe hang.
- **Loopback-only socket observation.** Binds `127.0.0.1` on an ephemeral port, listens, connects, accepts. Both `connect` and `accept` are non-blocking and bounded by a poll timeout, so the probe cannot hang on either. No external host is ever contacted.

What it explicitly does **not** do:

- It does not create, enforce, or attest to any boundary or container.
- It does not spawn Wine or execute Windows software.
- It reports **observations, not an attestation**. Every report carries `observationsOnly: true`, `runtimeIsolationImplemented: false`, `perAppBoundaryEnforced: false`, and a disclaimer, so the output cannot be mistaken for a security guarantee.

Exit codes: `0` on a produced report, `2` on a usage error.

## Packaging (`Packaging/`)

These files are provided **only because they can be stated accurately**. They are not applied by `swift build`, and nothing here signs anything.

- `Info.plist` — `CFBundleExecutable` = `DMX`, `LSMinimumSystemVersion` = `13.0`, and `CFBundleIdentifier` = `org.dimensionx.controlplane`. That value is a **project identifier only**: it is *not* reserved, and it grants no rights. A distributor must own (or be authorised to use) whatever identifier it actually ships, and must change this value when it does not own `org.dimensionx.controlplane`.
- `DMX.entitlements` — declares `com.apple.security.app-sandbox` = `false`. The GUI is a deliberately **unsandboxed** control-plane front end: it runs only the `dmx` executable *you* select, never launches untrusted code, and this package implements no runtime isolation. It declares **no** application groups (a shared container is not per-app isolation) and **no** bypass entitlements.

To assemble a `.app` manually from the SwiftPM binary:

svg

```
cd DimensionX/native
swift build -c release
APP=".build/DMX.app"
mkdir -p "$APP/Contents/MacOS" "$APP/Contents/Resources"
cp .build/release/DMX "$APP/Contents/MacOS/DMX"
cp Packaging/Info.plist "$APP/Contents/Info.plist"

# SwiftPM emits the localized strings as a separate resource bundle named
# "<PackageName>_<TargetName>.bundle" — here DMXNative_DMXCore.bundle. It MUST be
# copied into the app, otherwise `Bundle.module` cannot resolve the en/es
# Localizable.strings at runtime.
BUNDLE="$(ls -d .build/release/*DMXCore*.bundle 2>/dev/null | head -n 1)"
if [ -n "$BUNDLE" ]; then
  cp -R "$BUNDLE" "$APP/Contents/Resources/"
fi

# Signing requires an identity that YOU own. None is provided here, and nothing
# is signed unless you set DMX_CODESIGN_IDENTITY to a real identity you control,
# for example "Developer ID Application: <Your Org> (<TEAMID>)".
if [ -n "${DMX_CODESIGN_IDENTITY:-}" ]; then
  codesign --force --options runtime \
    --entitlements Packaging/DMX.entitlements \
    --sign "$DMX_CODESIGN_IDENTITY" "$APP"
else
  echo "DMX_CODESIGN_IDENTITY is not set; skipping codesign (the app stays unsigned)."
fi
```

There is **no** fabricated signing identity in this repository, and no documented step relies on bypassing signature or library validation.

## Tests: coverage and limitations

The suite below is **authored**, not **executed**. No Swift toolchain exists in the authoring environment, so none of these tests has been run and **no assertion here should be read as a passing result**. Everything is an unverified claim until you run `swift test` on macOS.

What the suite is written to assert:

- **Real CLI adapter tests** (`CLIAdapterTests`). Each test writes a POSIX shell script into a temp directory, marks it executable, and drives it through the real adapter. Coverage: envelope success/error/malformed decoding, nullable `runtime_digest`, `--root` ordering, argument passing without a shell, pre-launch validation (relative path, blank name), timeout termination, and launch failure for a missing executable.
- **Static entitlement policy tests** (`EntitlementPolicyTests`). These parse `Packaging/DMX.entitlements` and `Packaging/Info.plist` from disk and assert the policy: no bypass keys, no temporary exceptions, no shared container, an explicit `app-sandbox=false`, no debug-only keys, and a consistent Info.plist.
- **Localization coverage** (`LocalizationTests`). Every `L10nKey` resolves in both `en` and `es`, and both tables cover the same key set.
- **Contract decoding** (`ModelsDecodingTests`). Every documented result shape decodes, including nested `JSONValue` round-tripping.
- **Probe scoping** (`BoundaryProbeTests`). Denied/readable behavior on caller-supplied paths, loopback-only addressing, and the presence of the observations-only declarations.

Known test limitations (must be read alongside the results):

1. **None of these tests have been executed here.** There is no Swift toolchain in the authoring environment. The suite is written to be runnable, but its results are unknown until you run `swift test` on macOS.
2. **The adapter tests require `/bin/sh`** and a POSIX filesystem. They exercise *the adapter*, not the backend.
3. **The boundary probe tests observe the test runner's own process.** They therefore validate scoping and reporting, not any security property — there is no security property to validate, because none is implemented.
4. **The `SecTask` assertions only check wording**, not enforcement. A probe reporting "sandbox not enabled" is an observation, not a verdict.
5. **`swift test` on a machine without the resources processed** would surface as localization test failures; that would indicate a packaging problem, not a product behavior problem.
